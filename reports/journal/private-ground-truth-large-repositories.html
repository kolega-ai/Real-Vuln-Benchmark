ISSUE 19 — REALVULN JOURNAL

Five large repositories, private ground truth, and a harder test for scanners

Five pinned Python repositories now contribute to the main 208-repository leaderboard. We keep their vulnerability labels private, publish service-issued aggregate receipts, and see a substantial score drop on this slice of four submitted result sets.

By Faizan Raza·2026-11-14·Issue 19
private ground truthlarge repositoriesscanner resultsbenchmark methodology

Why add these repositories?

Small deliberately vulnerable applications are useful because their labels and scanner outputs can be inspected in public. They do not represent the full search problem in a mature codebase. We added pinned revisions of Airflow, NetBox, Odoo, Saleor and Sentry: five substantially larger Python repositories with 1,944 scored ground-truth rows in the current private authority. Their aggregate results feed the same F3 headline as the 203 existing public repositories. They are not a separate competition or a special scanner category.

Why keep the ground truth private?

Publishing exact vulnerability locations in real projects can function as a disclosure. We want to measure scanners against these repositories without making the labels, submitted finding locations or source snippets public. A versioned private scoring authority fixes the five source commits and ground-truth snapshot. A participant submits normalized finding locations to the scoring service over HTTPS; the service compares them in memory, discards those locations and returns an unguessable receipt ID. The public record contains aggregate counts, F3 and recall, the authority version and hash, and per-repository totals. It contains no finding file or ground-truth row.

This has a deliberate trade-off: readers can verify that the published counts and F3 agree, but cannot independently reproduce the private match decisions from public labels. A receipt proves that the service scored a submitted result set. It does not prove how that result set was produced, that every source file was examined, or who operated the scanner. Participants can inspect a receipt by ID; RealVuln decides which receipts enter the dashboard after an issue requests publication.

The published leaderboard treats Kolega as one scanner among the entrants. Its 60.02% five-repository score comes from the official saved submission and counts above. The five large repositories lower each of these four pooled scores. The other three private submissions report very few matched locations, so their large-repository F3 is near zero; the figures describe these submitted outputs, rather than every possible run of those models.

What the drop tells us

On these submissions, large-repository performance is a clear gap. More code means a scanner must prioritize where to look, carry context across files and preserve enough evidence to report precise locations. The result suggests substantial room to improve coverage and matching on mature repositories. The F3 by repository size chart lets readers inspect the relationship across completed runs, with smoothing stated in its information panel.

Repository size alone is not a proven cause of the decline. These five projects differ from the public corpus in vulnerability mix, code structure and labeling. The private matching contract uses category IDs and source spans, while the public matcher uses CWE identity; the three non-Kolega result sets also passed through a fixed private category adapter. Those differences, plus scanner coverage and harness behavior, may contribute to the gap. A like-for-like follow-up with a public input identity and controlled runs is needed before attributing a precise share to size itself.

How to take part

The private scores page looks up a receipt by ID. To request that a receipt be added to the dashboard, open a GitHub issue with the receipt number. The participant cannot publish their own score into the leaderboard. New external registration is not yet open; the methodology and private scoring documentation explain the current contract and its limits.
