ISSUE 13 — REALVULN JOURNAL

RealVuln 3.0.0: TypeScript/JavaScript, non-scoring entries, and per-language leaderboards

RealVuln 3.0.0 doubles the corpus to 140 repositories by adding 74 TypeScript/JavaScript apps, introduces non-scoring ground-truth entries, and splits the leaderboard by language.

By Faizan Raza·2026-09-02·Issue 13 of 13
vulnerability scanner benchmarksecurity scanner benchmarksast toolsLLM vulnerability detectionAI code securitytypescript security

Why this matters

Every previous issue of this journal described a Python benchmark. That was an honest limitation and we said so on the dataset page, but it left the most common question we get — "does any of this hold for JavaScript?" — unanswered. RealVuln 3.0.0 is the release that starts answering it, and in doing so it forced two methodology decisions we had been postponing: what to do with a reviewed location that cannot be graded, and how to rank scanners that have not all seen the same code.

What we did

On 2026-09-02 we cut RealVuln 3.0.0 at 140 repositories: the unchanged 66-repo Python corpus plus 74 TypeScript/JavaScript applications. Twenty-four of the new repositories are community intentionally vulnerable apps (OWASP Juice Shop, NodeGoat, DVNA, DVWS and others), pinned by commit SHA to forks we control so the pins cannot drift. Fifty are company-style applications generated end-to-end by coding agents — Claude Opus 4.7, GPT-5.5 x-high, Kimi K2.6, DeepSeek V4 Pro and DeepSeek V4 Flash, ten each — across Express, Next.js, NestJS + Angular, Remix and Fastify + Vue, then seeded with reviewed vulnerabilities and published as single-snapshot public repositories. The TS/JS corpus contributes 2,236 vulnerable findings, bringing the dataset to 4,138 vulnerabilities and 280 false-positive traps; the traps are still Python-only, and we say so rather than pretend otherwise.

The second change is a new ground-truth state. Reviewing the TS/JS corpus produced 176 locations we could not settle from the source alone — cases where whether a finding is "a vulnerability" is a judgement call a competent reviewer could make either way. Previous releases had two choices for these, label them or delete them, and both are wrong: labelling grades scanners on a coin toss, deleting hides the location from anyone who wants to check our work. 3.0.0 keeps them in the ground truth with scoring: "non_scoring" and a written reason, and the scorer excludes them in both directions. A scanner that reports one is not charged a false positive; a scanner that misses one is not charged a miss. They take no part in matching at all, so a non-scoring row can never steal a match from a real one.

The third change is the leaderboard. Almost every scanner we have published so far ran on Python only, and so far five have covered both languages — Semgrep, DeepSeek V4 Flash, DeepSeek V4 Pro, GPT-5.6 Sol and Kolega DevSec Max V0.1.0. A sixth, Daybreak Blue, has TypeScript / JS coverage but no Python run yet, so it appears on that language's tab only and is left off the Overall ranking. Putting a 74-repo TS/JS score in the same column as a 66-repo Python score would be a comparison between different exams. The site now has language tabs — Overall, Python, TypeScript / JS — crossed with the existing authorship tabs. Every tab is like-for-like: the Overall tab ranks only scanners that covered all 140 repositories, and a run that covered one language is listed on that language's tab rather than being scored on code it never saw.

What we observed

The Python leaderboard is unchanged from 2.1.0 — same 28 scanners, same TP/FP counts, same F3 to the decimal — which was the point of leaving that corpus untouched. One label moved: the Python results published in 2.1.0 as Kolega DevSec Max V0.0.1 now sit under V0.1.0, because the TS/JS run is the same scanner and its Python path did not change; the numbers are identical and the old slug stays in the frozen 2.1.0 release. On the TypeScript / JS tab, Kolega DevSec Max V0.1.0 scores F3 82.7 at 91.5% recall and 44.5% precision across 74/74 repositories, with 33 of its reports on Juice Shop alone landing inside non-scoring locations and therefore counted as neither hit nor miss; across all 140 repositories its Overall F3 is 84.4. DeepSeek V4 Flash, the first third-party LLM scanner we ran on both corpora, scores F3 33.5 on TypeScript / JS at 32.8% recall and 41.6% precision — 734 true positives against 1,031 false positives over 74/74 repositories, for $2.33 of API spend in total. That is well below its Python F3 of 51.7, and its Overall figure is 41.8. DeepSeek V4 Pro, on the same prompt and harness, lands lower still on TypeScript / JS: F3 27.5 at 26.3% recall and 45.2% precision (589 true positives, 715 false positives, $3.85), against its Python F3 of 50.2, for an Overall figure of 38.0. The cheaper model beats the dearer one on both languages, and the gap is wider on TS/JS. GPT-5.6 Sol, run through the Codex CLI at its high reasoning-effort setting, is a different story: F3 72.1 on TypeScript / JS at 75.4% recall and 52.0% precision — 1,686 true positives against 1,558 false positives over 74/74 repositories — against a Python F3 of 53.9, for an Overall figure of 64.1, second only to Kolega. Its recall on TS/JS is higher than its own recall on Python, the opposite direction from both DeepSeek models. Sol runs on a ChatGPT subscription session rather than a metered API key, so its published cost is Codex's self-reported token estimate, not billed spend — a caveat that already applied to its Python figures and that we are surfacing explicitly for the first time here. In the course of that work we also found that this comparison itself sat on shaky ground: our Codex runner had no reasoning-effort control at all until this release, so the existing Python Sol figure was set at Codex's unrecorded ambient default rather than the high setting we now use for TS/JS — an apples-to-oranges gap we are correcting by re-running Python at high effort and by recording the setting in every run's metrics going forward. One TypeScript / JS result complicates the effort story further. Daybreak Blue — an OpenAI Codex alias that its own documentation says currently resolves to the same weights as GPT-5.6 Sol, differing only in the Daybreak program's defensive-cybersecurity system instructions — scores F3 79.2 on TypeScript / JS at 82.8% recall and 57.0% precision across all 74 repositories, second only to Kolega and well above plain Sol's 72.1. On a same-repo, same-effort pilot the gap was even starker: F3 88.3 against 57.1, with Daybreak Blue also holding a real precision lead (74.5% against 45.2%). If the underlying model really is identical, the entire difference comes from a system-prompt and safety-calibration change — a reminder that a benchmark entry names a full configuration, not just a model name. Daybreak Blue has no Python run yet, so it sits on the TypeScript / JS tab only and does not enter the Overall ranking. Semgrep scores F3 12.2 on TypeScript / JS at 12.3% recall and 11.0% precision — 276 true positives against 2,240 false positives over 74/74 repositories. That is higher than its Python F3 of 7.4, and its Overall figure lands at 10.0.

The non-scoring rows cluster where we expected: 64 of the 176 are in Juice Shop and 37 in its Goof fork, applications whose challenge design deliberately blurs the line between "vulnerable" and "intended". Twelve of the 74 TS/JS repositories carry at least one; sixty-two carry none.

Lines of code are now counted for every repository from its pinned tree rather than for Python only, excluding vendored third-party libraries checked into asset directories (a bundled three.js or jQuery is not code the repository's authors wrote): 741,034 in total, 607,252 of them TS/JS. Juice Shop alone is 45,003.

Why we think that happened

The Python results did not move because nothing that feeds them changed — the scorer's non-scoring path is inert on a corpus with no non-scoring rows, and we verified this by diffing the frozen 2.1.0 data against the new build before writing this entry.

The non-scoring count being concentrated in Juice Shop is a property of Juice Shop, not of our reviewers. It is a deliberately gamified application in which many "vulnerabilities" are challenge mechanics, so the question "would a production reviewer call this a defect?" is genuinely open far more often than in an ordinary codebase. Elsewhere the same standard triggered far less: the largest count outside the two Juice Shop variants is 23, in one generated CRM, and 62 of the 74 repositories have none.

The leaderboard split is a consequence we accepted rather than one we wanted. A single overall number is what everyone asks for, and with two languages and unequal coverage it would have been misleading. Restricting the overall table to full-coverage runs and showing the per-language tables alongside costs a click and buys an honest comparison.

What's next

The obvious gap is still third-party TS/JS results: three models are three data points, and the rest of the agentic LLM scanners we ran on Python need to run on the 74 new repositories before the TypeScript / JS and Overall tabs are full leaderboards. The three do not agree on direction — both DeepSeek models drop sharply from Python to TS/JS on the same prompt and harness (51.7 to 33.5 for Flash, 50.2 to 27.5 for Pro) while GPT-5.6 Sol rises (53.9 to 72.1) — so whatever is driving the Python/TS gap is not simply about the corpus; it interacts with the model or the harness. We are treating this as an open question rather than a conclusion until more model families report. False-positive traps for TS/JS are next in ground-truth work, and Java is the next language. As before, 3.0.0 is frozen at realvuln.com/v/3.0.0/ and every figure in this entry can be regenerated from the repository with make dashboard.
